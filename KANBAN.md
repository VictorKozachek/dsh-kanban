# Kanban-доска агентов в DeepSeek Harness

Набор для работы нескольких агентов в одном проекте: доска задач в правом
сайдбаре DSH Web, изоляция работы через git-worktree и протокол, по которому
агенты не пересекаются по файлам.

Проверяется на установленном DSH `0.2.1-rc.3` (приложение `desktop`): бандлы
берутся из приложения, а пакеты в `~/.dsh/profiles/node_modules` (там `0.1.5-rc.3`)
не монтируются. Плагин стоит в обоих профилях, живой GUI работает в `desktop`.
Первые версии набора делались под `0.1.5-rc.2` и профиль `web`.

Всё проверено по коду пакетов; что именно проверено, а что нет — в разделе
«Границы».

## Как доска выглядит

Макеты лежат в `dsh-kanban/docs/`:

| Файл | Что на нём |
|---|---|
| `board-mockup-panel-dark.png` | доска в правом сайдбаре, тёмная тема (4 колонки, дальше — прокрутка) |
| `board-mockup-panel-light.png` | то же в светлой теме |
| `board-mockup-full-dark.png` | только доска, все восемь колонок (бэклог первым) |
| `board-mockup-full-light.png` | то же в светлой теме |

Перерисовать после правок стилей плагина:

```bash
bin/render-mockup.sh          # PNG (PIL)
bin/render-mockup.sh --html   # ещё и HTML-версии для браузера
```

Макет не нарисован «на глаз»: `dsh-kanban/docs/dump-styles.mjs` достаёт из
`lib/client.js` ту же таблицу `styles` (и `COLUMNS`), которой пользуется плагин,
а `render-mockup.py` интерпретирует её значения — ширину колонки, отступы,
радиусы, `color-mix(... currentColor N%)`, цвета статусов. Поэтому макет
показывает реальные пропорции и цвета карточек; приблизительна только рамка
приложения вокруг (левый сайдбар и разговор — декорация для наглядности).

PNG рисуется через PIL, а не headless Chrome: под файловой песочницей DSH Chrome
не стартует, а PIL и Arial Unicode с кириллицей в системе есть.

## Установка

```bash
# 0. проекту нужен git: worktree без репозитория не создать
git init -b main && git add -A && git commit -m "init"

# 1. доска в профиль web (пакет объявляет dsh.bundle, поэтому ряд монтируется сам)
bin/install-kanban.sh

# 1a. то же для профиля desktop (Electron-приложение): dsh plugin для него
#     отказывается работать, поэтому пакет ставит сам скрипт
bin/install-kanban.sh desktop

# 2. перезапустить DSH Web — новый пакет читается при старте профиля
dsh web
```

Пресеты ролей (`dispatcher` / `worker` / `reviewer` / `verifier`) отдельной
командой ставить **не нужно**: определения едут вместе с плагином
(`dsh-kanban/presets/role-presets.json`) и регистрируются при каждом старте —
см. «Обновление плагина и пресеты». `bin/install-presets.sh` остаётся для старых
сборок DSH, где реестра пресетов ещё нет; если строки когда-то ставили руками,
их снимает `bin/install-presets.sh --takeover`.

После перезапуска: правый сайдбар → «+» в полосе табов → «Канбан» (или сразу
таб «Канбан», если он уже в наборе).

Профиль `desktop` — исключение: он управляется приложением, `dsh plugin` для него
не работает, поэтому `install-kanban.sh` делает то же самое сам — зависимость
`link:<путь>`, запись в `dsh.profile.bundles` и симлинк в `node_modules` профиля.

Скрипт **останавливается**, если в `cordis.patch.yml` профиля уже есть ручной ряд
`ui-kanban`: иначе плагин смонтируется дважды — из бандла и из вставки. Перейти с
ручной установки на штатную: `bin/install-kanban.sh <профиль> --takeover`.

**Два профиля — два способа установки.**

- `web` — штатно: в `~/.dsh/profiles/web/package.json` лежит
  `"dsh-kanban": "link:..."`, пакет добавлен в `dsh.profile.bundles`, профильный
  `cordis.patch.yml` не тронут. Откат: `dsh plugin --profile web remove dsh-kanban`.
- `desktop` (Electron-приложение) — тем же способом, но руками скрипта:
  зависимость `link:`, запись в `dsh.profile.bundles`, симлинк в `node_modules`
  профиля и **никакого** ряда `ui-kanban` в `cordis.patch.yml` — ряд приходит из
  бандла. Откат: убрать зависимость и бандл из манифеста профиля и удалить
  симлинк.

Оба профиля читают список бандлов при старте: после установки DSH Web
перезапускают (`dsh web`), приложение — закрывают и открывают заново.

## Как этим пользоваться

### Оркестратор

1. Создайте сессию в **основном чекауте** проекта (не в worktree) и выберите
   пресет `dispatcher`.
2. Дайте задачу словами. Оркестратор заведёт рабочее дерево `worktrees/007`,
   ветку и карточку внутри этой ветки (иначе исполнитель не увидит свою задачу —
   запись за пределы его рабочей директории запрещена):

   ```bash
   bin/task-new.sh "Починить экспорт QR"
   ```

   Доска увидит открытую задачу сама, синхронизация не нужна.

3. В GUI добавьте Workspace с путём `~/projects/<проект>/worktrees/007` (того
   проекта, где завели задачу) и создайте
   там сессию с пресетом `worker`. Каталог видимый и лежит прямо
   в корне проекта, так что в выборщике он выбирается обычным образом. Исполнителей
   с разными задачами можно вести параллельно — это разные Workspaces, разные
   ветки, разные песочницы.
4. **Закрепите карточку за сессией исполнителя** — иначе он её не возьмёт:
   протокол разрешает работать только с закреплённым за тобой.

   ```bash
   bin/task-move.sh 007 todo --owner "<session-id исполнителя>"
   ```

   В работе держите **не больше трёх задач** одновременно (сумма `in-progress`,
   `in-review`, `testing`); остальные ждут в `todo`.

   Задачи, нарезанные заранее, можно класть не в `todo`, а в бэклог — без
   владельца и роли. Оттуда их выдают асайном, FIFO по `id`:

   ```bash
   bin/task-new.sh --backlog "Следующая задача из спеки"
   # асайн: backlog → todo требует владельца, без него переход отвергается
   bin/task-move.sh 008 todo --owner "<session-id исполнителя>"
   ```

   `backlog → in-progress` запрещён: сначала выдача в `todo`, иначе исполнитель
   не получит наряд. `todo → backlog` возвращает задачу в очередь и снимает
   владельца. Дамп доски показывает бэклог первой строкой: `bin/board-status.sh`.

   Развязка `backlog → blocked → in-progress` идёт в два шага: у карточки из
   бэклога владельца нет, а снятие блокировки проверяет, что карточка закреплена.
   Сначала владелец пишется без смены статуса, потом снимается блокировка:

   ```bash
   bin/task-move.sh 008 blocked --owner "<session-id исполнителя>"
   bin/task-move.sh 008 in-progress --owner "$DSH_SESSION_ID"
   ```

   Осознанный обход обоих шагов — `--force`.

### Исполнитель (пресет `worker`)

```bash
bin/task-move.sh 007 in-progress --owner "$DSH_SESSION_ID" --role worker
# ... работа только в файлах задачи, тесты, коммит в ветку task/007 ...
bin/task-move.sh 007 in-review --role worker --tokens auto \
  --note "что сделано, как проверить, результат тестов"
```

`--tokens auto` пишет снимок расхода сессии в `tokens_worker` и пересчитывает
сумму `tokens`; источник — кэш проекций DSH, читает `bin/task-usage.sh`.

### Ревьювер (пресет `reviewer`)

```bash
bin/task-move.sh 007 testing --role reviewer --tokens auto --note "ревью пройдено: <что смотрел>"
# или
bin/task-move.sh 007 in-progress --role reviewer --tokens auto --note "замечания: <что вернуть исполнителю>"
```

### Тестировщик (пресет `verifier`)

```bash
bin/task-move.sh 007 ready --role verifier --tokens auto --note "проверил: тесты 12/12, сценарий X"
# или
bin/task-move.sh 007 in-progress --role verifier --tokens auto --note "не прошло: <причина и шаги>"
```

### Оркестратор (пресет `dispatcher`) коммитит

```bash
bin/task-commit.sh 007 --message "Починить экспорт QR"
# merge --no-ff с сообщением [007] Починить экспорт QR, карточка → merged
git worktree remove worktrees/007
```

Прямой `bin/task-move.sh 007 merged` протокол не разрешает: статус `merged`
ставит только `task-commit.sh`, чтобы сообщение коммита не осталось без правила.

**Пуш — шаг человека**, когда все задачи готовы и закоммичены:

```bash
git push <remote> <ветка>
```

Правило сообщения и разбор короткого имени ветки — в скиле
`.agents/skills/commit/SKILL.md`:

```
[{SHORT_BRANCH_NAME}] Message
release/NJ-001 → [NJ-001] …, task/007 → [007] …
```

Сессии и роли: команда одной задачи живёт в её Workspace (`worktrees/<id>`),
тестировщик приходит в тот же worktree отдельной сессией, а оркестратор сидит в
основном чекауте. Подробнее — `AGENTS.md`, раздел «Команды, сессии и роли».

### Доска

- Колонки: `backlog` → `todo` → `in-progress` → `in-review` → `testing` → `ready` → `merged`, плюс `blocked`.
  `backlog` — первая и нейтральная: это лог нарезанных задач, ещё не выданных
  исполнителю; карточка без владельца подписана «не назначено».
- Карточка показывает id, название, роль и владельца (id сессии), ветку,
  расход токенов (с разбивкой по ролям в подсказке), заметку и время.
- Значок «в ветке» — задача ещё не слита, карточка прочитана из рабочего дерева
  `worktrees/<id>`. Без значка — запись из основного чекаута (слитая или
  заведённая локально).
- **Человек двигает мышью только `backlog` ↔ `todo`** (перетаскиванием или
  кнопкой-дублем «→ В работу» / «← В backlog» на карточке). Вперёд — асайн:
  карточка получает `todo` и владельца, исполнителю уходит наряд. Назад — только
  из `todo`: `todo → backlog` снимает владельца и роль. Остальные колонки человек
  не двигает — их ведут агенты по протоколу; дроп в такую колонку показывает
  «эту карточку двигают только агенты».
- Пока запрос асайна идёт, кнопка неактивна и пишет «переношу…»; после успеха
  доска перечитывается, после отказа — короткий баннер с текстом хоста
  («все заняты», «карточка в статусе …») или «канал недоступен», если соединения
  с хостом нет.
- Обновление — опрос раз в 3 секунды (кнопка ⟳ — обновить сразу).
- Клик по заголовку карточки показывает имя файла.

### Бэклог, минимум `todo` и спецификации

Поток задач держится не на памяти оркестратора, а на файлах:

- **Спецификация** — `.kanban/specs/<NNN>.md`; номер — числовой префикс имени,
  поэтому `001-backlog.md` и `001.md` одинаково занимают 001, а новые спеки
  заводятся как `<NNN>.md`. Первый свободный номер
  выдаёт `bin/spec-new.sh "Название"` (статус, «Зачем», «Требования», «Вне
  скоупа»); оркестратор читает спеку и нарезает её на задачи. Карточка ссылается
  на спеку полем `spec` (годится и `NNN.md`, и `NNN-название.md`) и показывает
  её в панели деталей.
- **Нарезка** — `bin/task-new.sh "Название" --backlog --no-worktree --spec 001`:
  карточка ложится в `backlog` без владельца и роли.
- **Минимум очереди** — `.kanban/board.json` (tracked): `{ "minTodo": 3 }`. Это
  глубина `todo`: освободившийся исполнитель сразу получает следующую задачу.
  Файла нет — минимум 1; битый JSON — внятная ошибка, а не тихий ноль.
- **Пул исполнителей** — `.kanban/.workers.json` (в `.gitignore`), упорядоченный
  массив id сессий: порядок = приоритет выдачи. Файла нет — берётся единственный
  `worker` из `.kanban/.watcher-roles.json`.
- **Выдача** — `bin/backlog-fill.sh` (запускает оркестратор по наряду о
  недоборе): если `todo` меньше `minTodo`, берёт карточки `backlog` по возрастанию
  `id` (FIFO) и асайнит их свободным исполнителям переходом
  `backlog → todo --owner <id>`. Работает он **по слитому снимку доски**, а не по
  основному чекауту: обходит `.kanban/tasks` и доски рабочих деревьев
  (`worktrees/*/.kanban/tasks`, `.worktrees/*/.kanban/tasks`), из дерева берёт
  только одноимённую карточку `<id>.md` (унаследованные копии чужих карточек в
  счёт не идут, файл с чужим `id` внутри отбрасывается), а копии одной карточки
  сливает по свежести `updated` (равенство — в пользу дерева). Поэтому карточка,
  лежащая **только в ветке задачи**, тоже выдаётся: двигается её копия в рабочем
  дереве — копией `bin/task-move.sh` из этого дерева, и коммит `kanban(<id>): todo`
  уходит в ветку задачи. Занятость считается так же, по снимку: «занят» — у
  исполнителя есть карточка `in-progress` на любой доске проекта, поэтому
  устаревшая копия в основном чекауте занятую карточку не выдаст. Свободных нет
  или бэклог пуст — останавливается и говорит, где встал (в том числе «backlog
  исчерпан: выдано N из M»). Коды возврата: 0 — ок (включая «пополнять нечего»),
  1 — ошибка конфига или доски, 2 — неверный аргумент (`--min` с мусором и т.п.),
  3 — выдать не удалось. `--dry-run` показывает план
  и ничего не меняет, `--min N` переопределяет минимум.
- **Ручной асайн — `bin/task-assign.sh`** (это же запускает доска):
  `bin/task-assign.sh <id>` выдаёт конкретную карточку, `--dry-run` показывает
  план, `--unassign` возвращает её в очередь. Кого выбирает: «самый свободный» —
  у кого меньше карточек в конвейере `in-progress + in-review + testing` (по
  слитому снимку доски, с рабочими деревьями), занятому — у кого есть
  `in-progress` — асайн не делается; при равной нагрузке решает порядок
  `.kanban/.workers.json` (файла нет — единственный `worker` из
  `.kanban/.watcher-roles.json`). Если свободных нет или пул пуст, карточка
  остаётся в `backlog` и скрипт говорит об этом. Коды возврата: 0 — сделано
  (или `--dry-run` показал план), 1 — ошибка конфига или доски, 2 — ошибка
  использования, 3 — карточка не найдена или не в том статусе (асайн — только из
  `backlog`, возврат `--unassign` — только из `todo`: из `in-progress` уже нельзя,
  её взяли в работу), 4 — нет свободных исполнителей. Асайн пишет в карточку
  `owner` и `role: worker`; `since` остаётся пустым (правило `bin/task-move.sh`
  для `todo` — время роли ставится, когда карточку берут в работу); `--unassign`
  снимает `owner` и `role`. В GUI тот же скрипт вызывает host-канал
  `kanbanCardActions` (`dsh-kanban/lib/card-actions.js`): он сам проверяет статус
  карточки по слитому снимку доски и запускает скрипт из корня проекта без шелла,
  а в баннер доски уходит его `message`; коды 1/3/4 он превращает в подсказки
  «ошибка конфига или доски», «карточка не в том статусе», «все исполнители
  заняты».
- **Наряды сторожа** (чтобы поток не был немым, `dsh-kanban/lib/backlog-notices.js`):
  два наряда по состоянию доски, а не по переходу. **Асайн** — карточка оказалась
  в `todo` с непустым `owner`: владельцу уходит «тебе назначена #N, бери в работу»
  с точной командой и путём к карточке; на ту же версию карточки с тем же
  владельцем наряд не повторяется, а смена владельца в `todo` даёт новый.
  **Пополнение** — в `todo` стало меньше `minTodo`: оркестратору уходит «в todo N
  < M, пополни: `bin/backlog-fill.sh`» (если бэклог пуст, в тексте так и сказано —
  нужна нарезка спеки); сигнал один на недобор, повторно — только после того, как
  `todo` добрал до минимума и снова упал ниже. Оба наряда доставляются тем же
  путём, что и остальные (`sessionController.prompt`, режим `queue`), и помнятся
  той же парой файлов состояния. `.kanban/.watcher-state.json` хранит ключи
  **доставленных** нарядов — `<id>:<статус>:<updated>`, у асайна в ключе ещё и
  владелец, у недобора `board:refill:short`; по ним один и тот же наряд не
  повторяется при перезапуске. `.kanban/.watcher-pending.json` — наоборот,
  **недоставленные**: сам наряд с текстом, адресатом, рабочим деревом и временем
  попытки. Повтор — на старте профиля: сторож объявляет доску заново, а затем
  проходит по pending и отправляет то, что ещё живо (карточка на месте и в том же
  статусе); устаревшие следы — карточка уехала дальше или её уже нет на доске —
  снимаются молча. После успешной доставки ключ появляется в state, а след из
  pending удаляется; поэтому на старте доставленный асайн и недобор не
  повторяются, а недоставленные — повторяются.
- **Служебные файлы** — `.watcher-state.json`, `.watcher-roles.json`,
  `.watcher-pending.json`, `.workers.json`, `.kanban/worktrees.json` и каталоги
  `worktrees/` закрыты `.gitignore`: состояние доски живёт на машине, а не в
  репозитории. Карточки, спеки и `board.json` — наоборот, остаются в git.

### Завершение работы (graceful shutdown)

Плагин живёт в процессе профиля DSH, и закрывает этот процесс не он сам, а
оболочка. Поэтому «выключить плагин» значит снять всё, что держит host-половина,
и снять быстро: у процесса есть бюджет.

**Что держит host-половина** (`dsh-kanban/lib/index.js`). На каждую доску сторож
поднимает `fs.watch` на `.kanban/tasks` и на каждую доску рабочего дерева, а если
каталога `worktrees`/`.worktrees` ещё нет — на корень проекта, чтобы заметить его
появление. На пустой доске это два наблюдателя, на живом конфиге с `roots` —
десятки досок и, значит, десятки наблюдателей. Плюс таймеры: стартовый обход
доски (`catchUpMs`), debounce после события файловой системы (`debounceMs`),
проба командного канала.
Плюс работа в полёте: наряд — это `sessionController.prompt` со своим
`AbortController`, асайн из GUI — дочерний процесс `bin/task-assign.sh`
(`execFile` с `signal`), а служба `kanbanCardActions` зарегистрирована в контексте
плагина.

**Что гарантирует dispose.** Один `cleanup` с единым флагом `disposed`,
зарегистрированный через `ctx.effect` (cordis вызывает этот disposer при выгрузке
файбера плагина — это и есть настоящий путь shutdown). Флаг выставляется первым, и
после него не появляется ни наблюдателя, ни таймера, ни наряда, ни дочернего
процесса: события файловой системы, стартовые обходы, доставки и асайн из GUI
начинаются с проверки `disposed`. Затем отменяются дочерние процессы (общий
`AbortController` жизни плагина) и in-flight наряды (свой controller у каждой
доставки) — начатый `prompt` получает abort, `task-assign.sh` убивается, а не
живёт до своего таймаута; закрываются все `fs.watch`; снимаются таймеры, включая
таймер пробы канала; снимается регистрация службы канала. Повторный dispose
безопасен: второй вызов выходит по флагу.

**Почему при обновлении был таймаут.** До #053 cleanup висел на событии
`ctx.on("dispose", …)`, а cordis в этой версии его не эмитит: `ctx.effect`-disposer
вызывается, событие — нет. То есть весь блок освобождения был мёртвым кодом. Host
подтверждал shutdown (ack приходил примерно за секунду), но незакрытые `fs.watch`
держали event loop, и процесс не выходил вообще; оболочка ждала 10 секунд, убивала
Host и получала `DesktopHostUncleanExitError` — это и есть «приложение ждёт
перезапуск». Числами это показал харнесс #052: без плагина выход за ~2.8 с, с
плагином — `FSEventWrap×2` на одну доску и `×60` на тридцать после shutdown,
процесс приходилось убивать по бюджету.

**Бюджеты DSH.** В процессе профиля (`dsh/lib/profile-boot`, `createProcessShutdown`)
`PROCESS_SHUTDOWN_TIMEOUT_MS = 5e3`: дерево приложения должно дозакрыться за 5
секунд, иначе force-exit. У desktop-оболочки свой предел — 10 секунд на
`shutdown-complete` и выход, потом SIGTERM/SIGKILL. Отсюда требование к плагину:
dispose не ждёт ничего внешнего (никаких «дождусь ответа сессии»), а всё, что
нельзя закрыть мгновенно, отменяется по сигналу. Наш dispose закрывает ресурсы
сам и сразу: на 30 досках тест отводит ему бюджет 200 мс, и он в него
укладывается.

**Харнесс реального shutdown.** `bin/host-shutdown-check.mjs` поднимает настоящее
приложение (Electron в node-режиме + `dsh-desktop-host`) в изоляции: временный
`DSH_HOME` с профилем, собранным с нуля, временные доски, свободный порт (зашитый
в host-энтри `19387` подменяется в памяти хуком на `0`, бандл не меняется; живой
`~/.dsh` не читается). Сценарии: `control` — плагин выключен, `board` — одна
доска, `roots` — 30 досок под `roots`, `events` — 10 досок и записи в них накануне
shutdown. Скрипт печатает таблицу (время до `ready`, до `shutdown-complete`, до
выхода, код/сигнал) и возвращает 1, если сценарий не уложился в бюджет ack (5 с) и
выхода (10 с); если приложения нет (не macOS, другой путь) — понятный «пропуск» с
кодом 0.

```bash
bin/node.sh bin/host-shutdown-check.mjs                          # все четыре сценария
bin/node.sh bin/host-shutdown-check.mjs --scenario board --handles
```

Флаги: `--scenario`, `--repeat N`, `--handles` (снять живые handles через
inspector — сам inspector влияет на тайминги), `--verbose`, `--keep`,
`--settle N`; опечатка в аргументах — код 2, а не «тихий успех». Харнесс сам
определяет версию и раскладку установленного DSH (вход Host'а, рантайм,
динамический порт в 0.2.x) и печатает их в шапке; при падении до `ready`
показывает причину и stderr Host'а. Замер на `0.2.1-rc.3` (эта машина, после
#053 и #055): `control` 834/996/1014 мс, `board` 906/1070/1083,
`roots` 824/1014/1027, `events` 730/914/933 (ready/ack/exit), все с кодом 0 —
«все сценарии в бюджете». На `0.1.7` до фикса dispose с плагином процесс не
выходил вовсе и убивался по бюджету. В `bin/test.sh` харнесс не входит: он
поднимает настоящее приложение и медленный.

**Быстрая регрессия.** `dsh-kanban/test/shutdown.test.mjs` проверяет то же самое
без приложения, за миллисекунды: после выгрузки не остаётся живых `fs.watch` и
таймеров, dispose тридцати досок укладывается в бюджет (цель — 200 мс на
свободной машине; в тесте потолок выше, потому что закрытие 30 наблюдателей под
нагрузкой может занимать больше, а утечку ловит ожидание нулевых хендлов),
событие файловой системы
после dispose не поднимает watcher заново и не пишет state, in-flight `prompt`
получает abort (и отменённый наряд не попадает в `.kanban/.watcher-pending.json`),
дочерний `task-assign.sh` убивается вместо ожидания таймаута, повторный dispose
безопасен и снимает службу канала.

### Дочерние доски: обзор дерева команд

Компания — это иерархия команд (`backend` → `agents` → `ai-manager`), и у каждой
команды свой проект со своей доской. Сессия-родитель видит только свою доску,
поэтому у плагина есть **вторая вкладка «Дочерние доски»**: сводка по доскам
дерева и drill-down в доску ребёнка. Обзор **только читает** — асайн и переходы
остаются у ролей дочерней доски.

**Манифест.** Список досок лежит в `.kanban/children.json` в корне рабочей
директории родительской сессии:

```json
{ "version": 1,
  "boards": [
    { "path": "aif-project/infra", "title": "infra" },
    { "path": "/abs/path/to/other-project" }
  ] }
```

Относительные пути считаются от корня рабочей директории сессии, абсолютные
берутся как есть (доски вне дерева). `title` необязателен — по умолчанию
последний сегмент пути. Манифест с относительными путями переносим и годится в
git; абсолютные — машинно-зависимы.

**Генерация.** `bin/board-children.sh` обходит дерево и пишет манифест:

```bash
bin/board-children.sh --root ~/projects/ai-fabric/aif-project   # <root>/.kanban/children.json
bin/board-children.sh --root . --print                          # только показать, файл не писать
bin/board-children.sh --root . --depth 6 --out DIR/.kanban/children.json
bin/board-children.sh --root . --board /abs/other-project       # доска вне дерева
```

- доска — каталог с `.kanban/tasks`; корень тоже считается доской, если у него
  есть `.kanban/tasks`;
- `--root` можно не передавать — по умолчанию текущий каталог;
- `--depth N` — глубина вложенности **досок** (корень = 0, по умолчанию 4,
  допустимо 0…9); `--depth 0` — только корень; на деревьях глубже 4 поднимите
  значение. У сторожа своя ручка — `discoverBoards` с умолчанием 6, поэтому
  манифест по умолчанию может быть уже, чем наблюдение сторожа: это разные
  механизмы, и связаны они только тем, что оба ищут `.kanban/tasks`;
- пропускаются `node_modules`, `worktrees`, `.worktrees` и все скрытые каталоги
  (`.git`, `.idea`). Сторож дополнительно пропускает `dist`, `build`,
  `templates`, `target`: доска под `dist/` попадёт в манифест, но не в
  наблюдение — известное различие;
- `--base DIR` — база относительных путей (по умолчанию `--root`; доски вне базы
  пишутся абсолютными), `--board PATH` — добавить доску вне дерева (повторяемый);
- `--out FILE` — куда писать (по умолчанию `<root>/.kanban/children.json`),
  `--print` — только вывести в stdout; повторный запуск идемпотентен;
- коды: 0 — ок, 1 — не удалось записать, 2 — неверные аргументы или
  несуществующий `--root`/`--base`/`--board`.

**Вкладка «Дочерние доски»** (второй таб плагина рядом с «Канбан», в гиде
отдельной записью):

- дерево досок с отступами по путям; у доски — счётчики карточек по статусам
  (`backlog`, `todo`, `in-progress`, `in-review`, `testing`, `ready`,
  `blocked`; `merged` в счётчики не входит);
- карточки «в работе» (`in-progress`) с id, названием, владельцем/ролью и
  временем обновления;
- ошибка чтения доски — отдельной строкой у доски, остальные доски продолжают
  показываться; путь, которого нет, помечается «нет доски»;
- клик по доске — read-only вид её колонок с карточками, клик по карточке —
  детали (описание, токены, роль/владелец, `spec`); drag&drop, кнопок перевода и
  тоста «переношу…» здесь нет;
- обновление — опрос раз в 3 с и кнопка ⟳; пустые состояния различаются:
  манифеста нет (подсказка с командой), манифест не разобран, досок нет.

**Служба хоста.** `kanbanChildren` — обычный Typert remote только для чтения:
endpoint `kanbanChildren/read`, аргумент `{ request: { sessionId } }`, ответ
`{ ok: true, value: { boards, problems, manifest } }`. Хост сам находит каталог
сессии и манифест в нём, для каждой доски собирает снимок (`.kanban/tasks` плюс
`worktrees/*`, слияние карточек по свежести `updated` и «одноимённая карточка из
дерева» — те же правила, что у сторожа) и считает счётчики; ошибка одной доски
попадает в её `problems`/`missing` и не валит остальные. Изменяющих аргументов у
службы нет — вообще.

**Read-only — это не песочница.** Служба и вкладка не умеют писать, но если доски
детей лежат внутри workspace родителя, родительская сессия физически может писать
в них bash'ем. Для жёсткой изоляции держите dashboard-воркспейс вне дерева детей:
чтение по абсолютным путям работает и оттуда. (Вне скоупа спеки 004 — запрет на
запись в доски детей на уровне песочницы.)

**Не путать со сторожем.** Обзор детей и сторож независимы: сторож работает по
своему конфигу `boards`/`roots` и рассылает наряды, а служба обзора читает
манифест из каталога сессии и регистрируется даже без `boards`. Наряды по доскам
детей родителю не приходят.

**Как включить.** В сессии родителя (рабочая директория — корень дерева или
родительский проект) выполнить `bin/board-children.sh --root <дерево>`, затем в
правом сайдбаре «+» в полосе табов → «Дочерние доски». Образец дерева:
`~/projects/ai-fabric/aif-project` — 37 досок (корень тоже доска), включая
иерархию команд `backend/agents/ai-manager`, `backend/agents/ai-engineer`.

### Обновление плагина и пресеты

Пресет сессии — это её **id** в логе (`dispatcher`, `worker`, `reviewer`,
`verifier`). При рестарте DSH берёт *текущее* определение этого id и отвергает
отсутствующее: нет определения — сессия открывается стандартной, сторож не может
доставлять наряды, а сменить пресет у непустой сессии нельзя (это ограничение
DSH). Поэтому:

- **id пресетов стабильны и не переименовываются** — только добавляются новые.
  Правило релиза: id в логах пользователей должны резолвиться всегда.
- **Определения едут вместе с плагином** (`dsh-kanban/presets/role-presets.json`,
  генерируется `bin/gen-role-presets.sh`) и регистрируются host-половиной при
  каждом старте профиля (`dsh-kanban/lib/presets.js`). Обновление, сброс профиля
  или новая машина больше не «снимают» роли: плагин поднимает их сам.
- **Сессии после обновления пересоздавать не нужно.** id в логах сохранён, а
  определение появляется при старте — сессия открывается со своим пресетом и
  нарядами, без архивации парка.
- **Legacy-строки профиля больше не нужны.** Если `bin/install-presets.sh` когда-то
  ставил блок в `cordis.patch.yml`, он не мешает (плагин видит дубликат,
  предупреждает и оставляет существующее определение), но убрать его чище:
  `bin/install-presets.sh --takeover` удаляет блок между маркерами и не трогает
  остальной патч; повторный запуск идемпотентен. После этого предупреждений о
  дубликатах в логе нет.

**Чеклист обновления DSH.** Обновили приложение или пересобрали рантайм:

1. `bin/gen-role-presets.sh` — перегенерировать `presets/role-presets.patch.yml`
   и `dsh-kanban/presets/role-presets.json` из нового встроенного `standard`
   (в релизе это делает тот, кто собирает пакет; руками в профиле ничего не
   правится). Проверка свежести встроена в `bin/test.sh`.
2. `bin/install-kanban.sh` — только если плагина в профиле ещё нет (обновление
   пакета по `link:` подхватывается само).
3. Перезапустить профиль: определения пресетов регистрируются при старте.

### Смена пресета существующей сессии (офлайн)

DSH **не даёт** сменить пресет уже стартовавшей сессии: реестр пресетов
разрешает `select` только пустой сессии, для начатой бросает
`agent-preset/locked` (`dsh-agent-preset-registry`). Когда роль «слетела»
(issue #1) или пресет выбран не тот, остаётся архив сессии — либо офлайн-правка
лога инструментом `bin/session-preset.sh`.

**Как это законно.** Лог сессии append-only: `session.v4.jsonl.zstd` —
конкатенация независимых zstd-кадров, первый кадр — заголовок
(`{type:"session", version:4, …}`, заморожен как факт создания), дальше по кадру
на событие. Текущий пресет — проекция `agentPreset`: инициализируется
заголовком и продвигается событием `agent-preset/selected`. Поэтому при
**закрытом DSH** достаточно досыпать один новый кадр с таким событием
(`seq = lastSeq + 1`, `time = Date.now()`), и при следующем старте DSH соберёт
сессию по новой проекции. Оригинальные кадры не трогаются, перед правкой
создаётся бэкап лога. Правило «model-visible ⟺ logged» соблюдено — решение
записано в лог. **Нужен перезапуск DSH:** живая смена невозможна.

```bash
bin/session-preset.sh --list                          # сессии: cwd, пресет, seq, состояние
bin/session-preset.sh --session <id|prefix> --to worker
bin/session-preset.sh --cwd DIR --from standard --to worker --dry-run
bin/session-preset.sh --all --from standard --to worker --yes
bin/session-preset.sh --restore ~/.dsh/session-backups/<id>.<ts>.zst
```

**Что показывает план.** Сессии, их cwd из заголовка, текущий пресет (`seq` —
номер последнего события), откуда и куда меняем, роль для карты доски и путь
бэкапа. `--dry-run` печатает план и ничего не пишет; `--json` — тот же план
машиночитаемо; без `--yes` в неинтерактивном режиме инструмент откажется
(код 2), в терминале спросит подтверждение.

**Отказы** (код 1; код 2 — ошибки аргументов):

- **DSH запущен.** Живой процесс держит `flock` на `<сессия>/session.lock` (так
  же, как сам DSH), поэтому проверка честная, а не «по свежести файла». Если в
  `DSH_HOME` есть живой `SingletonLock` десктопного приложения — тоже отказ.
  Закройте DSH и повторите;
- **открытый ход** (`turn/start` без `turn/end`) — отказ без `--force`: менять
  роль посреди рассуждения можно только осознанно;
- **неизвестный пресет** — отказ, если id нет ни в артефакте плагина
  `dsh-kanban/presets/role-presets.json` (генерирует `bin/gen-role-presets.sh`,
  #062; запасной путь — корневой `presets/role-presets.json`), ни среди
  встроенных: `standard` и четыре роли плагина (`dispatcher/worker/reviewer/
  verifier`) известны всегда — их регистрирует сам плагин (самолечение, спека
  005); осознанный обход — `--allow-unknown`;
- **битый лог, не v4 или оборванный хвост** — отказ: дописывать за torn-кадром
  нельзя, а переписывать оригинальные кадры нельзя тем более. Такой хвост
  усечёт сам DSH при следующей записи — повторите после его старта.

**Бэкап и восстановление.** Перед правкой лог копируется в
`$DSH_HOME/session-backups/<id>.<ts>.zst` (`--no-backup` отключает).
`--restore FILE` возвращает лог из бэкапа — с ещё одним страховочным бэкапом
текущего состояния (`*.pre-restore.zst`) и проверкой, что файл после этого
читается. `--session` для восстановления не обязателен: id выводится из имени
бэкапа (`<id>.<ts>.zst`), флаг нужен только для нестандартно названного файла.

**Карта ролей.** Сторож заполняет `.kanban/.watcher-roles.json` по живым событиям
выбора пресета (`agent-preset/selected`), а офлайн-событие при рестарте не
эмитится — поэтому инструмент сам находит доску (ближайший родитель cwd сессии
с `.kanban/`) и пишет роль: `--role` или по имени пресета для
`dispatcher/worker/reviewer/verifier`. Пресет вне ролей (`standard`) снимает
запись этой сессии из карты; `--no-roles` карту не трогает.

**Осторожно.** Смена пресета — это смена системного промпта и набора
инструментов следующего хода: делайте её осознанно и между ходами. Для
восстановления после потери **определений** пресетов (issue #1) аптечка не
нужна — достаточно обновить плагин (#062): определения едут вместе с ним, и
сессии оживают сами, сохраняя свои id.

## Как устроена изоляция (и почему именно так)

Проверено по исходникам установленного DSH:

- **Корень песочницы сессии = её рабочая директория.**
  `dsh-sandbox-policy`: «One primary workspace root per session — policy resolves
  `SessionHeader.cwd`; extra writable roots are not part of
  `SandboxExecutionPolicy`». Дополнительных writable-корней нет, поэтому своя
  директория на задачу — единственный способ гарантировать непересечение.
- **Субагенты наследуют cwd родителя** и сменить его не могут. Значит фан-аут
  субагентами внутри одной сессии изоляции не даёт: он годится для чтения,
  тестов и задач без общих файлов.
- **Встроенной поддержки git-worktree в DSH нет** (по всем 241 пакету
  упоминаний нет) — worktree создаётся снаружи, скриптом.
- **GUI группирует сессии по каталогу**: разные пути — разные Workspaces, что
  и даёт «свою» сессию на каждый worktree без ручной настройки.
- **`workspaceFiles` — read-only Remote**: «The service exposes no mutation
  operation». Поэтому состояние и живёт в файлах, которые пишут агенты, а не в
  доске.
- **Запись — только внутрь своей директории, чтение — куда угодно.**
  Проверено на живом проекте: `mkdir` рядом с проектом песочница отклоняет, а
  внутри — разрешает. Отсюда два решения: рабочие деревья живут в
  `<проект>/worktrees/`, а карточка открытой задачи обязана лежать в ветке
  задачи — исполнитель физически не может писать в основной чекаут. Поскольку
  `worktrees/` находится внутри workspace, доска обходит его штатным `list` и
  не нуждается в манифесте; манифест остался только для деревьев вне проекта
  (там `list` не работает, а `read` по абсолютному пути — работает).
- **Фид изменений не видит записи из bash и редактора** (только инструменты
  `write`/`edit`). Поэтому доска опрашивает файлы, а не подписывается на фид.
- **Один процесс `dsh web` с N сессиями** предпочтительнее N процессов на одном
  `$DSH_HOME`: у `dsh-storage-json` нет межпроцессной блокировки, при двух
  процессах возможен last-write-wins по общим файлам состояния.

## Границы: что проверено, а что нет

Проверено:

- бандл плагина грузится как классический скрипт, `id` совпадает с именем
  пакета, `exports.apply`/`exports.inject` на месте — `dsh-kanban/test/parse.test.mjs`;
- разбор карточек, нормализация статусов (включая `in_progress`, `in-review`,
  `testing`, `заблокировано`), фильтрация не-карточек, обработка ошибок и
  исключений Remote;
- слияние карточек из worktree: более свежий `updated` побеждает, исчезнувший
  worktree молчит, настоящая ошибка чтения попадает в предупреждения, битый
  манифест не ломает доску;
- **панель деталей**: клик по карточке открывает её справа от колонок, клик по другой
  переключает, крестик закрывает, порядок комментариев — по появлению. Тест гоняет таб
  вручную (вызывает обработчики) и отдельно рендерит панель; макеты состояние по клику
  не изображают — на них доска без панели.
- **рендер доски целиком, без браузера**: `render.test.mjs` поднимает поддельный
  cordis-контекст, вызывает `apply` и рендерит тело слота мини-рендерером React
  (с настоящим порядком хуков и выполнением эффектов). Проверяется, что тип таба
  регистрируется как `extension` и попадает в гид, что словари и заголовок на
  месте, что карточки приходят через Remote, раскладываются по колонкам, внутри
  колонки сортируются по id, у карточек из worktree есть значок «в ветке», а у
  слитой — нет, что владелец обрезается по правилу, и что пустая доска
  показывает подсказку, а ошибка Remote — баннер;
- **чтение за пределами workspace разрешено, листинг — нет**: проверено по коду
  `dsh-api-workspace-files` — `confine()` (ошибка `outside-workspace`) вызывается
  ровно из одного места, листинга, а чтение файла идёт через `locateFile()` без
  проверки вложенности;
- полный цикл в реальном git-репозитории: `task-new.sh` создаёт worktree, ветку
  и коммитит карточку в неё; исполнитель берёт задачу **из своего worktree**;
  `board-sync.sh` собирает манифест; после слияния карточка со статусом
  приезжает в основной чекаут, `merged` и удаление worktree очищают манифест;
- **бэклог как статус**: `task-new.sh --backlog` заводит карточку со
  `status: backlog` и пустым владельцем, `backlog → todo --owner` закрепляет
  задачу, асайн без `--owner` и прыжок `backlog → in-progress` отвергаются, а
  `todo → backlog` возвращает в очередь и снимает владельца — регрессии в
  `bin/test-scripts.sh`; колонка `backlog` первой на доске и в макете —
  `render.test.mjs`, `mockup.test.mjs`, `merge.test.mjs` (порядок колонок
  совпадает в обеих половинах плагина);
- **выдача из бэклога и спецификации**: `bin/backlog-fill.sh` выдаёт карточки
  по FIFO до `minTodo` по слитому снимку доски — и карточку, лежащую только в
  ветке задачи (двигает копия `task-move.sh` из дерева, коммит уходит в ветку),
  а устаревшая копия в основном чекауте занятую карточку не выдаёт; соблюдает
  `.workers.json` (занятой сессии не выдаёт, fallback — `worker` из
  `.watcher-roles.json`), `--dry-run` не трогает файлы, а битый `board.json`,
  пустой и исчерпанный бэклог дают коды 1 и 3 — все случаи в
  `bin/test-scripts.sh` на временных досках и настоящих git-worktree;
  `bin/spec-new.sh` заводит `.kanban/specs/<NNN>.md` с первым свободным номером,
  считая числовой префикс имени (`001-backlog.md` занимает 001, дыра 001/003/004
  даёт 002), `task-new.sh --spec 001` работает и со слагом и пишет поле `spec`,
  несуществующая спека отвергается, поле видно в панели деталей
  (`render.test.mjs`); `.gitignore` закрывает `.watcher-*`, `.workers.json` и
  `worktrees/`, но не карточки, спеки и `board.json`;
- **наряды асайна и недобора**: на временной доске с поддельным
  `sessionController` карточка в `todo` с владельцем даёт ровно один наряд
  владельцу (повтор на ту же версию не уходит, смена владельца — новый наряд),
  недобор `todo` будит диспетчера один раз и повторяется только после пополнения
  и нового падения, нет `board.json` или он битый — минимум 1, роль диспетчера не
  задана — наряд пропускается без падения — `assignment.test.mjs`;
- **наряды из рабочих деревьев**: снимок доски собирается из основного чекаута и

  берётся только одноимённая карточка), переход в дереве даёт наряд с путём
  дерева, наряд о слиянии идёт без приписки, уборка дерева и битые каталоги не

- **graceful shutdown**: dispose закрывает наблюдателей и таймеры, отменяет

- **обзор дочерних досок**: манифест `.kanban/children.json` разбирается

  и «в работе» — `children.test.mjs`; вкладка регистрируется вторым табом с

- `bin/gen-role-presets.sh` + `bin/install-presets.sh`: строки пресетов собираются

  профиля идемпотентно; `--takeover` убирает этот блок, сохраняя остальной патч

  сообщение `[КЛЮЧ] Message`, карточка уходит в `merged`, повторный коммит
  отвергается, а прямой `ready` → `merged` через `task-move.sh` закрыт;
- **живая активация плагина**: перезапуск профиля прошёл, таб «Канбан» в правом
  сайдбаре появился и рисует доску;
- **границы песочницы на живом проекте**: `mkdir` рядом с проектом отклонён, внутри
  проекта — разрешён; отсюда рабочие деревья переехали в `worktrees/`;
- **обход `worktrees/` настоящим читателем плагина** на реальных файлах проекта:
  находятся и карточка из основного чекаута, и карточка открытой задачи со
  значком «в ветке»; наследованные копии карточек основной ветки игнорируются.

Что применяется без перезапуска — проверено живьём на этой доске:

- **правки патч-слоя профиля** (`~/.dsh/profiles/<профиль>/cordis.patch.yml`) —
  загрузчик читает его живьём: роли пресетов появились в списке при создании
  сессии без перезапуска приложения;
- **правки клиентского бандла** (`dsh-kanban/lib/client.js`) — подхватываются
  **обновлением страницы**: бандл отдаётся из смонтированного пакета. Без
  обновления страницы правку увидит только dev-режим (`pnpm run dev:web` в чекауте
  DSH); в обычной работе считайте, что нужен F5;
- **host-код плагина** (`lib/index.js`) и **строка плагина** (её `config`) —
  читаются при старте профиля: сторож доски заработал только после перезапуска
  приложения, и роль тестировщика в его конфиге — тоже.

Состояние на момент последней правки: набор в `main`, `bin/test.sh` зелёный,
открытых рабочих деревьев нет.

Если таб не появился — смотрите `dsh --profile web --dump-config | grep -n kanban`
и консоль браузера: активация клиентского плагина падает громко, с указанием
пакета и пути.

## Развитие (v2)

Текущая версия намеренно читает файлы и ничего не пишет. Если понадобится
перетаскивание карточек, переходы с проверкой и атрибуция в реальном времени:

1. Host-плагин со `storageDomain` (`ctx.storageDomain.open(...)`), состояние в
   `$DSH_HOME/storages`.
2. Свой Typert-remote (`kanban/list`, `kanban/move`, `kanban/claim`) и стрим для
   живых обновлений — образец: связка `dsh-goal` + `dsh-client-ui-goal`.
3. Инструмент `kanban_move` для агентов (`ctx.tools.register(defineTool(...))`) —
   вызов инструмента не файловая операция, поэтому песочница не мешает.
4. Опционально — доска не табом, а полноширинной панелью: слот `main` плюс
   иконка в `sidebar.panellist` с тем же id (тогда доска занимает центр, а не
   правую колонку).

## Диагностика

| Симптом | Что проверить |
|---|---|
| Нет таба «Канбан» | `dsh --profile web --dump-config \| grep -n kanban`; перезапущен ли `dsh web` после установки |
| Таб есть, доска пуста | существует ли `<рабочая директория сессии>/.kanban/tasks`; карточки ли это `*.md`, кроме `README.md` |
| Карточка не переезжает | поле `status` в front matter; после правки руками обновите `updated` |
| `task-move.sh` пишет «недопустимый переход» | таблица переходов в `.kanban/tasks/README.md`; осознанный обход — `--force` |
| `task-move.sh` пишет «merged ставит только bin/task-commit.sh» | слияние идёт через `bin/task-commit.sh` из основного чекаута |
| После обновления плагина сессии «стали стандартными», сторож не шлёт наряды | плагин старой версии без самолечения пресетов: обновите пакет до версии с `dsh-kanban/lib/presets.js` и перезапустите профиль. Если пресеты ставили вручную (`bin/install-presets.sh`), уберите их блок: `bin/install-presets.sh --takeover`. Архивировать и пересоздавать сессии **не нужно** — id пресета в логе сохранён, определение появится при старте (см. «Обновление плагина и пресеты») |
| При обновлении приложение «ждёт перезапуск» и не закрывается | незакрытые ресурсы плагина: прогоните `bin/node.sh bin/host-shutdown-check.mjs` — сценарии должны выходить сами; раздел «Завершение работы (graceful shutdown)» |
| Правки клиента не видно на доске | обновите страницу (F5): без dev-режима горячей подмены клиента нет |
| Правки host-кода или строки плагина не действуют | перезапустите профиль: host-код и `config` строки читаются при старте |
| Сторож не разбудил роль | перезапущен ли профиль после правки конфига; верны ли id сессий в `roles` (они меняются, когда роль пересоздают в GUI) |
| Сторож объявил наряд дважды | это признак смены версии карточки: ключ доставки — `id:status:updated`, в файле `.kanban/.watcher-state.json` |
| `task-move.sh` пишет «не закреплена» | карточку не выдал оркестратор: `bin/task-move.sh <id> todo --owner <session-id>`; проверка владельца — при взятии из очереди и снятии блокировки |
| `task-move.sh` пишет «backlog → todo — это асайн» | карточку выдают из бэклога сразу с владельцем: `bin/task-move.sh <id> todo --owner <session-id>` |
| `task-move.sh` пишет «владелец меняется только им самим» | карточка закреплена за другой сессией; переназначение — осознанно, с `--force` |
| `task-commit.sh` пишет «ветки task/<id> нет» | работа по задаче уже в основной ветке: `bin/task-commit.sh <id> --no-merge --reason "почему слияния нет"` |
| Ревьювер вернул карточку, а она снова не у исполнителя | `owner` — это исполнитель задачи и не должен меняться при передачах; `role` показывает, кто держит карточку сейчас |
| `task-commit.sh` пишет «не в статусе ready» | карточку ещё не принял тестировщик; слияние — только из `ready` |
| `backlog-fill.sh` пишет «битый JSON» или «нет целого minTodo» | `.kanban/board.json` должен быть объектом с числом: `{ "minTodo": 3 }` |
| `backlog-fill.sh` пишет «нет свободных исполнителей» | у всех из `.kanban/.workers.json` есть карточка в `in-progress`: добавьте исполнителя или дождитесь освобождения |
| `backlog-fill.sh` пишет «backlog пуст» | нужна нарезка новой спеки: `bin/spec-new.sh "Название"` и `bin/task-new.sh "..." --backlog --spec <NNN>` |
| `task-new.sh --spec` пишет «нет файла .kanban/specs/…» | сначала заведите спеку `bin/spec-new.sh`; подходит и `<NNN>.md`, и `<NNN>-название.md` (номер — префикс имени) |
| Сообщение коммита без `[КЛЮЧ]` | сливали мимо `bin/task-commit.sh`; правило — в скиле `commit` |
| Открытая задача не видна на доске | оркестратор не запустил `bin/board-sync.sh`; проверьте `.kanban/worktrees.json` и `bin/board-sync.sh --print` |
| В worktree «карточка не найдена» | задача заведена старым скриптом (карточка в основном чекауте) — пересоздайте задачу или скопируйте карточку в ветку |
| Агент пишет «file access denied» | он работает не в своей рабочей директории: задача для оркестратора |
| `bin/test.sh` пишет «нужен node» | `bin/node.sh` не нашёл Node: задайте `DSH_NODE=/путь/к/node` |
| Вкладка «Дочерние доски» пуста | нет `<рабочая директория сессии>/.kanban/children.json`: соберите манифест `bin/board-children.sh --root <дерево>` (сначала проверьте `--print`) |
| Вкладка пишет «манифест не разобран» | битый JSON в `.kanban/children.json`: пересоберите `bin/board-children.sh --root <дерево> --out .kanban/children.json` |
| Доска в списке помечена «нет доски» | путь в манифесте битый: относительные считаются от корня рабочей директории сессии, абсолютные — как есть; пересоберите манифест |
| Сессия стала `standard`, роль не получает наряды | проверьте `bin/session-preset.sh --list`; при закрытом DSH — `--session <id> --to worker --yes`, затем перезапустите DSH. Если пропали сами определения пресетов (issue #1) — сначала обновите плагин (#062) |
| `session-preset: DSH держит сессию` | приложение ещё живо (занят `flock` на `session.lock`): закройте DSH и повторите |
| `session-preset: открытый ход` | ход не закрыт (`turn/start` без `turn/end`): дождитесь конца хода, либо осознанно `--force` |
| Вкладки «Дочерние доски» нет | плагин старый (до #059) или не перезапущен после обновления; обновите страницу и профиль, проверьте `dsh --profile web --dump-config \| grep -n kanban` |
| `git worktree add` не удался | проект не git-репозиторий или каталог worktree уже занят |
| Двое взяли одну задачу | правило протокола: занимать задачу сразу через `bin/task-move.sh ... --owner` |
