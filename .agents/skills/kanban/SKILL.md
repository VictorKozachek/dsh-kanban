# Скил: работа с доской задач

Доска — это каталог `.kanban/tasks/` в корне проекта, один файл `<id>.md` на
задачу. Сама доска в правом сайдбаре DSH Web файлы не пишет, а показывает их:
движения делают агенты через `bin/task-move.sh` (правит поле `status` и
коммитит карточку в текущую ветку) и — только между `backlog` и `todo` —
человек из GUI, командой host-каналу, который запускает `bin/task-assign.sh`
(см. «Человек в цикле»). Остальные переходы делают только роли по протоколу.
Карточка твоей задачи лежит **в твоём worktree** (она приходит с веткой задачи),
поэтому статус уезжает в слияние вместе с работой.

Роль не обязана помнить, что делать дальше: host-половина плагина
(`dsh-kanban/lib/index.js`) следит за доской и сама присылает наряд в сессию —
карточка вернулась в работу, ушла в ревью/на тесты/на слияние, появилась в
`todo` с владельцем (асайн) или `todo` стал меньше минимума (пора пополнять).
Получив наряд, сверься с карточкой: если она уже ушла дальше, наряд устарел.

## Взять задачу

1. Возьми карточку, **закреплённую за тобой**: `status: todo` и `owner` — твой
   `$DSH_SESSION_ID` (или ту, которую назвал пользователь):

   ```bash
   grep -lE "^owner: \"?$DSH_SESSION_ID\"?$" .kanban/tasks/*.md
   ```

   Если за тобой ничего не закреплено — не бери чужое и нераспределённое: скажи
   оркестратору, он выдаст задачу. `task-move.sh` откажет в переходе
   `todo` → `in-progress` для незакреплённой карточки: это протокол, а не сбой.
   Карточку в `backlog` сам не берут вовсе — её выдаёт оркестратор (см.
   «Статусы: колонки и бэклог»).

2. Прочитай карточку целиком: важны «Критерии готовности» и «Заметки».
3. Убедись, что задача ещё свободна и что другой агент её не взял.
4. Займи задачу **сразу**, одним изменением:

   ```bash
   bin/task-move.sh 007 in-progress --owner "$DSH_SESSION_ID" --role worker
   ```

5. Работай только в своей рабочей директории и только с файлами этой задачи.

## Статусы: колонки и бэклог

Колонки доски: `backlog` → `todo` → `in-progress` → `in-review` → `testing` →
`ready` → `merged`, плюс `blocked`. `backlog` — первая и нейтральная: это лог
нарезанных заранее задач, которые ещё не выдали исполнителю.

- **Карточка в `backlog`** — `owner: ""`, `role: ""`. Где она лежит, зависит от
  того, как задачу завели: штатный `bin/task-new.sh` кладёт её в ветку задачи
  (`worktrees/<id>/.kanban/tasks/<id>.md`, в основной чекаут она попадает только
  слиянием), а `--no-worktree` — сразу в основной чекаут
  (`.kanban/tasks/<id>.md`). Асайн правит ту копию, которую видит доска: из
  дерева берётся одноимённая карточка, и команду выполняют там же (у дерева своя
  копия `bin/task-move.sh`).
- **Асайн** — выдача карточки в `todo` с владельцем. Делает его оркестратор
  (`bin/task-move.sh 008 todo --owner <id>`, где `<id>` — сессия исполнителя) или
  человек из доски (`bin/task-assign.sh 008` сам выбирает самого свободного —
  см. «Человек в цикле»). Переход `backlog → todo` без `--owner` отвергается:
  без владельца исполнителю не ушёл бы наряд.
- **Из бэклога сразу в работу нельзя**: `backlog → in-progress` недопустим —
  сначала асайн в `todo`, потом исполнитель берёт задачу.
- **Возврат в очередь**: `bin/task-move.sh 008 backlog` (`todo → backlog`)
  снимает владельца и роль — задача снова ждёт выдачи.
- **Блокировка до выдачи**: `backlog → blocked` разрешён. У такой карточки
  владельца нет, поэтому в работу её поднимают в два шага — сначала забрать
  себе (`bin/task-move.sh 008 blocked --owner <свой id>`, статус не меняется,
  пишется владелец), потом снять блокировку
  (`bin/task-move.sh 008 in-progress --owner "$DSH_SESSION_ID"`). Осознанный
  обход — `--force`.
- **Наряды сторожа.** Асайн (`todo` с владельцем) будит этого исполнителя:
  «тебе назначена #N, бери в работу». Недобор `todo` — меньше `minTodo` из
  `.kanban/board.json` — будит оркестратора: «пополни: `bin/backlog-fill.sh`».
  Повторов нет: асайн не повторяется на ту же версию карточки с тем же
  владельцем (смена владельца в `todo` даёт новый наряд), сигнал о недоборе —
  один на недобор, пока `todo` не доберёт до минимума. Пул исполнителей для
  выдачи — `.kanban/.workers.json` (нет файла — единственный `worker` из
  `.kanban/.watcher-roles.json`).
- **Спецификации.** Спека — `.kanban/specs/<NNN>.md`; номер сквозной, и им служит
  числовой префикс имени, поэтому в репозитории спека лежит со слагом
  (`001-backlog.md`), а `bin/spec-new.sh "Название"` заводит `<NNN>.md` с первым
  свободным номером. Карточка ссылается на спеку полем `spec`:
  `bin/task-new.sh "…" --backlog --no-worktree --spec 001` — параметр принимает
  номер, а файл скрипт находит сам: `001.md` или `001-название.md`
  (несуществующая спека отвергается с подсказкой завести её). Спека — основание
  нарезки: оркестратор читает её и заводит карточки в `backlog`.

## Человек в цикле

Человек в GUI двигает карточку **только между `backlog` и `todo`** —
перетаскиванием или кнопкой-дублем на карточке («→ В работу» / «← В backlog»):

- `backlog → todo` — **асайн**: карточка достаётся самому свободному исполнителю
  (меньше всего карточек в конвейере `in-progress + in-review + testing`, при
  равенстве — порядок `.kanban/.workers.json`; у всех есть `in-progress` — отказ,
  карточка остаётся в `backlog`). В карточке появляются `owner` и `role: worker`,
  исполнителю уходит обычный наряд.
- `todo → backlog` — **возврат в очередь**: владелец и роль снимаются, асайна нет.

Колонки `in-progress`, `in-review`, `testing`, `ready`, `merged` и `blocked`
человек не двигает — их ведут только роли по протоколу (в GUI дроп в такую
колонку отвечает «эту карточку двигают только агенты»). Что это значит для ролей:

- **исполнитель**: `owner` в `todo` может появиться без оркестратора — это ручной
  асайн из доски. Задача выдана тебе: бери её в работу как обычно.
- **ревьювер и тестировщик**: их колонки из GUI не двигаются, поведение прежнее;
  карточку, которую человек вернул из `todo` в `backlog`, снова выдадут асайном,
  когда она понадобится, — ждать её в своей колонке не нужно.

## Сдать задачу

Перед сменой статуса проверь себя по списку:

- [ ] критерии готовности из карточки выполнены;
- [ ] тесты/сборка прогнаны **в этой же рабочей директории**;
- [ ] изменения закоммичены в ветку задачи;
- [ ] общие файлы (`package.json`, lock-файлы, схемы, миграции) не тронуты —
      если без них не обойтись, это задача оркестратора, а не твоя;
- [ ] в карточке есть `note` с тем, что сделано и как это проверять.

```bash
bin/task-move.sh 007 in-review --role worker --tokens auto \
  --note "Готово: <что сделано>. Проверка: <как проверить>. Тесты: <результат>."
```

Дальше карточку ведут другие роли: ревьювер (`in-review` → `testing`), затем
тестировщик (`testing` → `ready`). Исполнитель в это время свободен и берёт
следующую задачу из `todo`.

## Ревью и тестирование

- **Ревьювер** читает диф задачи, а не только заметку: принял —
  `bin/task-move.sh 007 testing --role reviewer --note "ревью пройдено: <что смотрел>"`, нашёл
  замечания — пишет их **в карточку** и возвращает её в `in-progress`
  (`--role reviewer --tokens auto --note "что вернуть: по пунктам"`). Карточка
  уходит обратно исполнителю: `owner` не меняется, `role` становится `worker`.
  Код задачи не правит.
- **Тестировщик** проверяет независимо: прошло —
  `bin/task-move.sh 007 ready --role verifier --note "проверил: <тесты и сценарий>"`, не прошло —
  `in-progress` с причиной и шагами воспроизведения.

## Если нашёл проблему при проверке (роли ревьювера и тестировщика)

```bash
bin/task-move.sh 007 in-progress --role reviewer --note "Не прошло: <что именно>. Шаги воспроизведения: <...>"
```

Не правь код задачи сам: верни её владельцу с точной причиной.

## Если нужна внешняя развязка

```bash
bin/task-move.sh 007 blocked --note "Ждём: <кого/чего>. Без этого <что не работает>."
```

## Частые ошибки

- **Правка `status` руками без `updated`.** Доска покажет карточку, но порядок
  и время будут врать. Пользуйся `bin/task-move.sh`.
- **Взятие задачи без `owner`.** Двое возьмут одну задачу.
- **Работа вне своего worktree.** Песочница откажет; если очень нужно — это
  задача для оркестратора.
- **Пометка `testing` без прогонов тестов.** Тестировщик вернёт карточку, а
  время будет потеряно.
- **Прыжок через ревью.** `in-progress` → `testing` скрипт отвергнет: сначала
  `in-review`, а в `testing` переводит уже ревьювер.
- **Взял чужую или нераспределённую карточку.** Задачи выдаёт оркестратор: бери
  только закреплённое за тобой, иначе двое сделают одну работу.
- **Переписал владельца чужой карточки.** Так выдачу обходили бы в два шага:
  `owner` меняет только сам владелец, переназначение — осознанно, через `--force`.
- **Взял карточку из бэклога сам.** `backlog → in-progress` недопустим, а
  асайн без `--owner` отвергается: задачу из `backlog` выдаёт оркестратор, после
  чего исполнителю приходит наряд «бери в работу».
- **Ждёшь наряд, а карточка в `todo` без владельца.** Асайн не сделан: пока в
  `owner` пусто, будить некого — попроси оркестратора закрепить карточку.
- **Закоммитил лишнее.** Правки задачи коммитятся по путям: `git add <файлы>`,
  а не `git add -A`. Иначе в коммит уезжают чужие и служебные файлы — в практике
  набора так в задачу уехали 103 чужих файла, включая секреты Jupyter.
- **Ревью устаревшей версии.** Пока шло ревью, карточку могли досдать: сверь её
  `updated` и хеши файлов с тем, что было в начале. Изменилась — перечитай карточку
  и проверяй текущую версию, прежние выводы отбрось; иначе вердикт уйдёт не про
  тот код.
- **Забыл `--tokens auto`.** Тогда расход задачи не попадёт в карточку и анализ
  затрат будет неполным: снимок пишется только в момент передачи.
- **Мерж и пуш не твоё дело.** Ветку вливает оркестратор и только через
  `bin/task-commit.sh`; `git push` из сессии агента не делает никто — пуш
  запускает человек, когда все задачи готовы и закоммичены.
