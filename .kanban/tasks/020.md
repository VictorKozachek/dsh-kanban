## Задача
Сейчас команду на работу даёт человек: карточка вернулась в `in-progress`, а сессия
исполнителя об этом не узнает, пока в неё не напишут. Нужно убрать человека из
этого цикла: host-плагин следит за карточками и сам отправляет наряд в нужную
сессию.

**Выбранный путь (решение владельца):** событийный watcher + prompt. Опрос
через `schedule` и «команда внутри одной сессии» отклонены.

## Что известно про API
- Сообщение в сессию: сервис `sessionController`, метод `prompt(request)` —
  тот же, которым пользуется GUI (`packages/api/session-controller/src/index.ts`,
  `@Remote('prompt')` → `SessionCommandController.prompt`). При занятой сессии
  отвечает `session/agent-busy`, при неизвестной — `session/not-found`.
- Слежение: обычный `fs.watch` на каталог доски + debounce; DSH-обёртки не нужно.
- Место: host-половина уже установленного плагина `dsh-kanban` (`lib/index.js`,
  сейчас пустой `apply`) — новый пакет не нужен, но правки host-кода требуют
  перезапуска профиля.

## План
1. Выделить чистую часть: снапшот карточек → переходы (было/стало) → решения
   «кому и что отправить». Тестируется на фикстурах без сессий.
2. Watcher: корни досок из конфига плагина, `fs.watch` + debounce, сравнение
   снапшотов по `id/status/owner/role/note`.
3. Правила наряда: карточка ушла в `in-progress` → **владельцу** (`owner`);
   `in-review` → сессии-ревьюверу, `testing` → сессии-тестировщику, `ready` →
   оркестратору (их id берутся из конфига: у карточки есть только `owner`).
4. Отправка через `sessionController.prompt`; `agent-busy` — отложить и повторить
   (или пропустить с записью в лог), `not-found` — в лог.
5. Подтверждение: писать в карточку строку «наряд доставлен <кому> <когда>» или
   только в лог — решить в реализации.
6. Тесты: чистая часть + фейковый `sessionController`; прогон `bin/test.sh`.

### Ограничение, которое надо решить

`roles.*` хранит id сессий, а они меняются, когда роль пересоздают в GUI. Пока
это ручное поле. Правильное решение — определять роль сессии по её пресету
(`reviewer`/`verifier`/`dispatcher`) и подставлять автоматически; вынести
отдельной карточкой или дописать сюда.

### Дополнение: стартовый обход

Переходы — не единственный случай. Карточка, которая уже висит в `in-review` на
момент старта сторожа, перехода не даёт и осталась бы без наряда. Теперь на старте
сторож разбирает текущий снимок и объявляет `in-review`/`testing`/`ready`;
повторы при следующих перезапусках гасит `.kanban/.watcher-state.json`
(ключ `id:status:updated`, файл в `.gitignore`).

Тесты сторожа: 20 проверок, включая стартовый снимок и статус в наряде.
