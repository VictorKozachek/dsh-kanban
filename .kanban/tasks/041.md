## Задача

Разблокировать параллельную работу нескольких исполнителей. Сейчас сторож
наблюдает только `<board>/.kanban/tasks` основного чекаута, поэтому переходы
карточек в рабочих деревьях (`worktrees/<id>/.kanban/tasks/<id>.md`) не видны и
наряды не уходят — из-за этого проект ведётся в одном рабочем каталоге, где два
исполнителя мешают друг другу. Нужно научить сторожа видеть доски рабочих
деревьев и сливать их с основной.

Что сделать (строго в этих файлах):

1. `dsh-kanban/lib/index.js`:
   - вместо `readSnapshot(tasksDir)` по одному каталогу — снимок доски из трёх
     источников: `<board>/.kanban/tasks`, `<board>/worktrees/*/.kanban/tasks`,
     `<board>/.worktrees/*/.kanban/tasks` (оба имени каталога деревьев
     используются в проекте; манифест `.kanban/worktrees.json` для деревьев
     **вне** проекта — не в этой задаче);
   - слияние по id карточки: побеждает более свежий `updated`; при равенстве и
     пустом `updated` — копия из рабочего дерева (та же семантика, что в
     клиентской половине, `dsh-kanban/lib/client.js` + `test/merge.test.mjs`);
     нечитаемый/исчезнувший каталог или файл — пропустить, не падать;
   - стартовый снимок, `fs.watch` и `tick` — по слитому снимку (следить за
     появлением/удалением самих каталогов worktrees не обязательно: карточка
     меняется при переходе, а он происходит в уже существующем дереве; новый
     worktree появляется вместе с карточкой — её увидит следующий тик по
     событию в основном `.kanban/tasks`... **проверь это**: если тик не
     срабатывает, добавь наблюдение за `<board>/worktrees` с тем же `debounceMs`);
   - текст наряда для карточки с непустым `worktree:` должен указывать рабочее
     дерево задачи (путь из поля `worktree`): «карточка в
     worktrees/<id> — работай там», команды выполняются из этого каталога.
     Дописывай это в `deliver`, не меняя `planNotices` — `watcher-core.js` в
     этой задаче трогать нельзя (он параллельно правится в #038).
2. Новый тест `dsh-kanban/test/worktree-watch.test.mjs` + строка запуска в
   `bin/test.sh`. Стенд без git: временный каталог с
   `.kanban/tasks` и `worktrees/039/.kanban/tasks`, поддельный
   `sessionController` как в `delivery.test.mjs`. Обязательные случаи:
   - переход карточки в рабочем дереве (`in-progress → in-review`) даёт наряд
     ревьюверу и именно с путём рабочего дерева в тексте;
   - более свежий `updated` из рабочего дерева побеждает копию в основном
     чекауте (и наоборот — старая копия из дерева проигрывает);
   - удалённое рабочее дерево: карточка остаётся из основного чекаута;
   - переход карточки в основном чекауте по-прежнему даёт наряд;
   - один наряд на версию карточки (файл состояния), без дублей;
   - битый/пустой каталог в `worktrees/` не ломает обход.
3. `bin/test.sh` — только добавление запуска нового теста.

Не трогать: `dsh-kanban/lib/watcher-core.js`, `dsh-kanban/lib/client.js`,
`bin/task-move.sh`, `bin/task-new.sh`, `bin/board-status.mjs`, существующие
тесты, `KANBAN.md`, `AGENTS.md`, `package.json` — они принадлежат другим
задачам. Это граница файлов, не пожелание: #038 идёт параллельно.

## Критерии готовности

- [ ] `bin/test.sh` зелёный, включая новый `worktree-watch.test.mjs`.
- [ ] На временной доске переход карточки в `worktrees/039/.kanban/tasks`
      порождает ровно один наряд нужной роли; текст содержит путь
      `worktrees/039`.
- [ ] Слияние по `updated` совпадает с клиентской семантикой (свежая копия
      побеждает, равенство — в пользу рабочего дерева).
- [ ] Удаление дерева и битые каталоги не ломают обход и не дают ложных нарядов.
- [ ] Основной чекаут продолжает работать как раньше (регрессий в
      `delivery.test.mjs` нет).
- [ ] Вне работы: после слияния хост-половина подхватится только после
      перезапуска приложения — в карточке отметь, что для живой проверки нужен
      рестарт профиля (это сделает оркестратор).
