## Симптом (со слов пользователя)

Чтобы сторож поднялся после перезапуска и снова начал раздавать наряды, приходится
запускать приложение из терминала:

```bash
"/Applications/DeepSeek Harness.app/Contents/MacOS/DeepSeek Harness" 2>&1 | tee /tmp/dsh.log
```

При обычном запуске (Finder / `open -a`) host-половина не раздаёт наряды, хотя
клиентская половина (вкладка доски) работает. Ранее это же наблюдалось в #2:
после рестарта наряды не шли, пока не перезагрузить строку плагина через
`pluginManager/setPluginEnabled` (HMR) — то есть подозрение на **порядок
инициализации при холодном старте**, а не на логику сторожа (после reload всё
работает).

## Гипотезы (проверить по диагностике холодного старта)

1. **Профильный оверрайд строки** `~/.dsh/cordis.patch.yml` содержит
   `- id: ui-kanban` + `config:` без `name: dsh-kanban`; документация DSH про
   override слоёв говорит перечислять поля строки. Если при холодном старте
   оверрайд не сливается с bundle-строкой, entry может активироваться без
   модуля/не активироваться вовсе (а HMR-reload это маскирует).
2. **Порядок применения (inject)**: `apply` зависит от `sessionController` +
   `agentPresets`; если холодный старт даёт apply с пустым/частичным конфигом
   или до готовности сервисов — сторож не стартует. Запись `applies[].config`
   покажет.
3. **stdout-зависимость**: терминальный запуск даёт открытый pipe stdout;
   обычный — закрытый. Если host-половина что-то пишет в `process.stdout`
   без защиты, запись может ронять инициализацию (в нашем коде `log()` и
   диагностика защищены, но проверить стоит).

## Инцидент 11.11: heartbeat уронил Host (моя регрессия)

Сразу после старта Host упал с:

```
dsh: fatal uncaught exception: ReferenceError: disposed is not defined
    at Timeout._onTimeout (file:///Users/victor/projects/dsh-kanban/dsh-kanban/lib/index.js:516:5)
```

Причина: в коммите `7bdcd86` heartbeat-таймер зарегистрирован **вне** `try`,
а `disposed` был объявлен **внутри** `try` (другая область видимости). Через
20 секунд таймер падал с необработанным `ReferenceError`, Host завершался с
кодом 1; пользователю пришлось временно отключить плагины.

Исправлено в `6f7283e`:
- `disposed` объявлен в начале `apply` (до heartbeat);
- heartbeat: настраиваемый `heartbeatMs` (для тестов), `unref()`, снимается в
  `cleanup`, при раннем выходе и в `catch`;
- регрессия в `delivery.test.mjs`: apply с `heartbeatMs: 5`, ожидание 40 мс —
  старый код ронял процесс, новый проходит.

**Следствие для диагностики холодного старта:** предыдущий снимок
`/tmp/dsh-kanban-watch.diag.json` снимался с Host, который затем упал из-за
heartbeat, поэтому вывод «финальный Host не применил плагин» требует
перепроверки на чистом запуске после `6f7283e`.

## Второй дефект: зависшие доставки (11.11, после хотфикса heartbeat)

Хост больше не падает (crash-логи только до 18:00), apply успешен, но на живом
Host видно: `deliver-once` есть, `delivered`/`prompt-failed` нет, state-файлы не
обновлялись, pending пуст — доставки **зависали**. Вероятная причина: десятки
холодных сессий, `observeSession`/`prompt` не отвечают, а сторож одновременно
штурмует 47 досок.

Исправлено (`08c7f1f`):
- семафор доставок (`deliveryConcurrency`, по умолчанию 3);
- таймаут `prompt` (`deliverTimeoutMs`, 15 с) через `Promise.race` — при
  зависании наряд уходит в pending, а не висит вечно;
- таймаут `cwd` (`cwdTimeoutMs`, 5 с) через race; при таймауте prompt не
  вызывается, наряд в pending;
- `sessionCwdFromContext` освобождает lease и для `Symbol.asyncDispose`;
- регрессии: зависший prompt → pending; зависший `observeSession` → prompt не
  вызывается, pending есть.

Дальше: перезагрузить строку плагина/приложение, снять диагностику и проверить,
что наряды доходят, а таймауты видны в событиях (`deliver-timeout`,
`cwd-timeout`) и pending. Если prompt систематически не отвечает для холодных
сессий — отдельный вопрос к DSH (возможно, нужен `resume` перед `prompt` или
другой режим).
