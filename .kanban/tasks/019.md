## Задача
Карточки 006, 007, 009 и 013 — инфраструктура самого набора, и их работа сделана
прямо в `main` обоих репозиториев, без ветки задачи. По протоколу же после
`testing` идёт `ready`, а закрывает карточку только `bin/task-commit.sh`, который
мержит ветку `task/<id>`. Ветки нет — значит карточку не закрыть штатно: она
застрянет в `ready`, а `--force` обесценит правило «сливает только оркестратор».

Нужно решение: либо у `task-commit.sh` появляется штатный путь «работа уже в
main» (например `--no-merge` с обязательной заметкой), либо такие задачи обязаны
идти через worktree, как все остальные.

- [x] карточку, чья работа уже в `main`, можно закрыть одной командой, и это не
      `--force` вслепую: команда требует объяснения, почему слияния нет
- [x] есть тест на новый путь закрытия

## Что поправить (вернул ревьювер)

Проверено и принято: отказ без `--reason` (код 2), отказ при существующей
ветке, закрытие `--no-merge` (карточка `merged`, заметка, ни одного
merge-коммита, в main ничего не влито), отказ обычного режима без ветки (в том
числе `--dry-run`), честный `--dry-run` в обоих режимах, чистое дерево только
для слияния, обычное слияние и повторный отказ, живая #006 (закрыта без
merge-коммита). Осталось одно:

- [ ] `bin/task-commit.sh:151` — guard «ветка существует» смотрит только на
      эффективный `$BRANCH`, а его перебивает `--branch` (строка 48). Достаточно
      передать несуществующее имя — и `--no-merge` проходит, хотя ветка задачи
      жива. Проверено: репозиторий, карточка 001 в `main` в `ready`, ветка
      `task/001` с несделанным коммитом (`w.txt`); без `--branch` отказ, а
      `--no-merge --reason "уже в main" --branch task/опечатка` → exit 0, карточка
      `merged`, `task/001` осталась неслитой (1 коммит, 0 merge-коммитов). Это
      ровно то, от чего защищает пункт: режим стал способом не сливать настоящую
      ветку. Правка: проверять и `$BRANCH`, и `task/$id` (для беcветочной задачи
      оба не существуют — законный путь не страдает).
      Симптом рядом: если карточка лежит в worktree, а `--branch` указан в никуда,
      скрипт доходит до `task-move.sh` в main и падает с «карточка не найдена»,
      а следом печатает «статус merged не записан: поставьте его вручную»
      (`bin/task-commit.sh:225-228`) — сообщение намекает, что слияние было.
- [ ] (мелочь) `bin/task-commit.sh:50` — `--reason ""` (пустое значение отдельным
      аргументом) падает на `${2:?}` с bash-ошибкой «2: --reason требует
      значения» и кодом 1, вместо внятного отказа с кодом 2; форма `--reason=`
      даёт правильный код 2. Причина из одних пробелов (`--reason "   "`)
      проходит и пишет заметку «закрыто без слияния:» без текста.
- [ ] (мелочь) `bin/task-commit.sh:191-205` — `--no-merge --dry-run` печатает
      «целевая ветка: main» и «сообщение коммита: …», хотя в этом режиме
      merge-коммита не будет; лишние строки сбивают. `--reason` без `--no-merge`
      (обычное слияние) молча игнорируется — стоит хотя бы предупредить.

## Сделано
Выбран вариант владельца: режим у того же скрипта, чтобы «в merged только через
`task-commit.sh`» осталось правдой.

- `--no-merge` требует `--reason`: без причины отказ с подсказкой
- при существующей ветке `task/<id>` режим отказывает — это обычное слияние
- причина пишется в карточку заметкой «закрыто без слияния: …»
- проверка наличия ветки добавлена и в обычный режим, и в `--dry-run`: раньше
  dry-run печатал план и выходил 0, даже когда ветки нет — та самая тишина,
  из-за которой #006 выглядела «готовой к слиянию»
- чистое дерево требуется только для слияния: у `--no-merge` слияния нет
- шесть регрессий в `bin/test-scripts.sh`; `AGENTS.md` и `KANBAN.md` дополнены
