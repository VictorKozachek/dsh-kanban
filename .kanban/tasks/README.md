# Карточки задач

Один файл = одна задача. Имя файла: `<id>.md` (например `007.md`). Доска
(`dsh-kanban` в правом сайдбаре) читает этот каталог и рисует колонки по полю
`status`.

**Где лежит карточка.** У открытой задачи — в её ветке, то есть в рабочем дереве
`<проект>/worktrees/<id>`: только там исполнитель может её править, потому что запись
за пределы своей рабочей директории запрещена песочницей. В основной чекаут
карточка попадает слиянием ветки; там её и видит оркестратор как итоговую запись.

Доска находит открытые задачи сама: обходит `worktrees/<id>/.kanban/tasks` и
берёт **только одноимённую карточку** `<id>.md` — рабочие деревья наследуют все
карточки основной ветки, и те уже представлены своими записями. Такие карточки
помечены значком «в ветке». Манифест `.kanban/worktrees.json` (его пишет
`bin/board-sync.sh`) нужен только для рабочих деревьев **вне** проекта.

Файлы `README.md` доска игнорирует, остальные `*.md` — читает.

## Формат

```markdown
---
id: "007"
title: Короткое название задачи
status: todo            # todo | in-progress | in-review | testing | ready | merged | blocked
owner: ""               # id сессии, которая держит карточку ($DSH_SESSION_ID)
role: ""                # worker | reviewer | verifier | dispatcher
tokens: ""              # сумма по всем ролям (считается автоматически)
tokens_worker: ""       # снимок расхода сессии исполнителя на момент передачи
since: ""               # с какого времени карточка у текущей роли
                        # по роли на каждую роль: tokens_reviewer, tokens_verifier
branch: task/007        # ветка worktree
worktree: /abs/path     # рабочая директория задачи
updated: 2026-01-01T12:00:00Z
---

## Задача
Что нужно сделать.

## Критерии готовности
- [ ] проверяемый пункт

## Заметки
Ссылки, решения, результаты тестов, причина блокировки.
```

## Порядок назначения

Задачи **выдаёт оркестратор**, по порядку id: карточка закрепляется за
конкретной сессией до начала работы —

```bash
bin/task-move.sh 007 todo --owner <session-id исполнителя>
```

Исполнитель берёт только закреплённое за ним:

```bash
grep -lE "^owner: \"?$DSH_SESSION_ID\"?$" .kanban/tasks/*.md
```

Нераспределённую карточку (`owner: ""`) самовольно не берут — её закрепит
оркестратор; исключение — ручной запуск, когда он прямо сказал взять эту задачу.
Скрипт это проверяет: переход `todo` → `in-progress` для незакреплённой или чужой
карточки отвергается (`--force` — осознанный обход).

Проверка касается **только взятия из очереди**. Возврат карточки в работу
(`in-review` / `testing` / `ready` / `blocked` → `in-progress`) делает ревьювер или
тестировщик: он проходит без `--force`, `owner` (исполнитель задачи) не меняется, а
`role` становится `worker` — карточка вернулась тому, кто её делает.

Поля владения: `owner` — **исполнитель задачи**, ставится один раз при взятии из
очереди и дальше не меняется; `role` — роль, которая держит карточку сейчас
(`worker` → `reviewer` → `verifier`).
Так две сессии не могут взяться за одну работу: копии карточки в разных worktree
не видят чужих правок до слияния.

В работе держат не больше трёх задач одновременно (сумма `in-progress`,
`in-review`, `testing`); если ревьювер или тестировщик занят, карточка ждёт в
своей колонке, а исполнитель берёт следующую закреплённую за ним.

## Кто какой статус ставит

| Переход | Кто | Когда |
|---|---|---|
| `todo` → `in-progress` | исполнитель | взял задачу, вписал свой `owner` |
| `in-progress` → `in-review` | исполнитель | работа закончена, тесты локально прошли, ветка закоммичена |
| `in-review` → `in-progress` | ревьювер | есть замечания: пишет их в карточку и возвращает **её же** исполнителю; в `note` — что именно поправить |
| `in-review` → `testing` | ревьювер | код принят, карточка уходит тестировщику |
| `testing` → `ready` | тестировщик | проверка прошла, карточка уходит оркестратору |
| `testing` → `in-progress` | тестировщик | проверка не прошла; в `note` — причина и шаги воспроизведения |
| `ready` → `merged` | оркестратор | только через `bin/task-commit.sh`: merge с сообщением `[{короткое имя ветки}] Message` |
| `ready` → `in-progress` | оркестратор | слияние конфликтует: задача возвращается владельцу |
| `todo` / `in-progress` / `in-review` / `testing` / `ready` → `blocked` | исполнитель | нужен человек: ответ или действие, которое ИИ не сделает сам |
| `blocked` → `in-progress` | исполнитель | развязка получена, работа продолжается |

Роль, которая двигает карточку, пишет себя в поле `role` (`--role worker` и так
далее) — доска показывает её на карточке рядом с владельцем, а `since` — с какого
времени карточка у неё.

Вместе со статусом роль записывает снимок своего расхода токенов:
`--role worker --tokens auto`. Скрипт `bin/task-usage.sh` берёт счётчики из
кэша проекций DSH (`$DSH_HOME/storages/session_projcache/sessions/<id>.json`),
пишет их в `tokens_<роль>` и пересчитывает сумму `tokens`. Если роль не названа
или кэша ещё нет, поле не пишется — мусор в карточку не попадает.

**Занятую карточку чужой не забирает:** если в `owner` стоит другой id,
переход в `in-progress` отвергается (обход — `--force`). Параллельно можно
вести сколько угодно задач, но каждая — в своём worktree и со своим
исполнителем; две роли на одной карточке одновременно не работают.

`bin/task-move.sh` знает протокол и отвергает недопустимый переход; осознанный
обход — `--force`. Исключение — `merged`: его ставит только `bin/task-commit.sh`,
потому что вместе со статусом собирается сообщение коммита по правилу
`[{SHORT_BRANCH_NAME}] Message` (скил `commit`).

`git push` не делает ни один агент: пуш запускает человек руками, когда все
задачи готовы и закоммичены. Повторная запись того же статуса (обновить `owner` или
`note`, не двигая карточку) разрешена всегда.

Пресеты ролей: `worker` (исполнитель), `reviewer` (ревьювер), `verifier`
(тестировщик), `dispatcher` (оркестратор). Ставятся `bin/install-presets.sh`,
описание ролей — в `AGENTS.md`.

Протокол целиком — в `AGENTS.md` в корне проекта.
