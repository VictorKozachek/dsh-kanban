# Спека 001: колонка backlog и автопополнение todo

Статус: принята, нарезана на задачи #038–#040.

## Зачем

Оркестратор получает спецификацию, изучает её и нарезает задачи заранее — они
складываются в `backlog` без роли и владельца. Это «лог задач»: видно, что
впереди, и ничего не теряется между срезами. Когда в `todo` задач меньше
минимума, оркестратор достаёт следующую из `backlog`, закрепляет за первым
свободным исполнителем и кладёт в `todo` — исполнитель получает наряд и берёт её
в работу. Пришла новая спецификация — оркестратор повторяет нарезку.

## Модель

- `backlog` — полноценный статус карточки, а не синоним `todo` (сегодня
  `backlog` в обеих половинах плагина — алиас `todo`; алиас убирается).
- Карточка в `backlog` — обычная карточка: `status: backlog`, `owner: ""`,
  `role: ""`, заполнены `title`, тело задачи и критерии готовности.
- Порядок выпуска — FIFO по `id` (порядок нарезки). Поле приоритета не вводим.
- Колонка `backlog` — первая слева, перед `todo`, нейтрального цвета; карточки
  без владельца показываются как «не назначено».

## Спецификации

- Каждая входящая спецификация — файл `.kanban/specs/<NNN>.md` (номер сквозной,
  как у задач). Заводит оркестратор: `bin/spec-new.sh "Название"`.
- Карточка ссылается на спеку полем `spec: "<NNN>"` (появляется в задаче #039
  вместе с полем в парсере `FIELDS`).
- Нарезка остаётся работой оркестратора, автоматики «спекa → задачи» нет.

## Минимум todo и выдача

- Минимум задач в `todo` — `.kanban/board.json` (tracked): `{ "minTodo": 2 }`.
- Пул исполнителей — `.kanban/.workers.json` (в `.gitignore`): упорядоченный
  список id сессий; fallback — единственный `worker` из `.kanban/.watcher-roles.json`.
- «Свободен» = у исполнителя нет карточки в `in-progress` (правило «один
  `in-progress` на агента»); `in-review`/`testing`/`ready` исполнителя не занимают.
- `bin/backlog-fill.sh` — ручной запуск оркестратором (полуавтомат, выбран
  осознанно: «задачу выдаёт оркестратор»): считает `todo`, если меньше
  `minTodo` — берёт карточки `backlog` по возрастанию id, закрепляет за первым
  свободным исполнителем и двигает в `todo`. Есть `--dry-run` и отчёт; если
  свободных нет или `backlog` пуст — понятный вывод и код возврата.

## Наряды сторожа (чтобы поток не был немым)

1. **Назначение.** Карточка оказалась в `todo` с непустым `owner` — владельцу
   уходит наряд «тебе назначена #N, бери: `bin/task-move.sh N in-progress ...`».
   Без этого асайн из `backlog` никто не увидит (сейчас сторож будит только на
   возвратах, ревью, тестах и `ready`).
2. **Пополнение.** В `todo` стало меньше `minTodo` — оркестратору уходит наряд
   «пополни `todo` из `backlog`». Повторов нет: сигнал по состоянию, а не по
   каждому тику доски.

## Переходы протокола

- `backlog → todo` — только оркестратор, с `--owner` (асайн).
- `todo → backlog` — оркестратор возвращает задачу в очередь (например, при
  пересмотре плана).
- `backlog → blocked` — разрешён (задача упёрлась в вопрос ещё до выдачи).
- Из `backlog` сразу в работу нельзя: асайн идёт через `todo`, чтобы исполнитель
  получил наряд.

## Вне скоупа

- Сторож пока не обходит `worktrees/<id>/.kanban/tasks` (переходы карточек в
  рабочих деревьях он не видит). Поэтому задачи этой фичи и текущий режим работы
  ведутся в основном чекауте (`bin/task-new.sh --no-worktree`). Это отдельный
  долг, в спеку не входит.
- Приоритеты, дедлайны, автоматическая нарезка спецификаций, drag-and-drop.

## Приёмка фичи

Живой сценарий на доске: спецификация в `.kanban/specs/`, пачка карточек в
`backlog`; после того как `todo` опускается ниже `minTodo`, оркестратор получает
наряд, запускает `backlog-fill.sh`, карточка уезжает в `todo` с владельцем,
исполнителю приходит наряд об асайне, он берёт её в `in-progress`. `bin/test.sh`
зелёный, колонка `backlog` видна в GUI.
